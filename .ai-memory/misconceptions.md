# Agent Misconception & API Log

## Active Warnings

- **Container service checks:** `systemctl is-active <unit>` cannot see host daemons from inside a container — it false-negatived on a running libvirtd. Judge host services by connecting (e.g., `virsh -c qemu+unix:///system version --daemon`), never by systemctl. *(Logged: Phase 0)*
- **Zed terminal sandbox:** Blocks unix-socket syscalls — `virsh` failed with "Failed to create socket: Operation not permitted" under the default sandbox. Run libvirt/vagrant commands with `unsandboxed: true`. *(Logged: Phase 0)*
- **Zed terminal sandbox:** Sandboxed `vagrant plugin list` silently printed nothing (stderr was discarded) and hid an installed system plugin (vagrant-libvirt 0.11.2). Re-check plugin/tool state unsandboxed before concluding anything is missing. *(Logged: Phase 0)*
- **Agent environment:** Container already mounts host libvirt sockets (`/run/libvirt/libvirt-sock`, mode 0666). `/dev/kvm` is NOT needed in-container when driving host libvirtd via socket — QEMU runs on the host. Do not ask the user to recreate the container for VM access. *(Logged: Phase 0)*
- **sudo:** Requires a password in this container; agent cannot `dnf install`. Route package installs through the user. *(Logged: Phase 0)*
- **Frida CLI:** Directive's verification `frida -p <PID> --version` is invalid — `--version` prints CLI version and exits without attaching. Correct attach check: `frida -H <host> -p <PID> -q -e "console.log(Process.arch)"`. *(Logged: Planning)*
- **vagrant-libvirt:** The default libvirt management network is NAT'd to the internet; leaving it attached silently defeats guest isolation. Use `mgmt_attach: false` + qemu-guest-agent address discovery. *(Logged: Planning)*
- **Windows ISO taxonomy:** `...19041.1_MULTI...` is Windows 10 2004 consumer multi-edition media — NOT LTSC (LTSC 2021 = build 19044 family, single-edition MVS-named ISO). "IoT Enterprise LTSC" is a separate edition with separate licensing; user license is non-IoT. uupdump consumer 21H2 chains contain no LTSC edition — the dedicated "Windows 10 Enterprise LTSC 2021" chain must be selected. *(Logged: Phase 1)*
- **bsdtar on MVS ISOs:** `bsdtar -tf` on the LTSC 2021 UDF ISO lists only `.` and `README.TXT` (broken UDF traversal). Use `7z l <iso>` to inspect such ISOs. *(Logged: Phase 1)*
- **Zed terminal permission parser:** Rejects any command containing `$VAR`/`$(...)` interpolation — including harmless `for` loops — even when unsandboxed. Write literal commands with no shell variables. *(Logged: Phase 1)*
- **op CLI:** `op account list` works while signed out (shows configured accounts); `op whoami` → "account is not signed in". Account configured ≠ authenticated — always probe `op whoami` before attempting `op read`. *(Logged: Phase 1)*
- **Packer 1.16:** The QEMU builder is NOT bundled with the core binary anymore — `source "qemu"` fails with "Unknown source type qemu" until a `required_plugins` block (github.com/hashicorp/qemu) is declared and `packer init` has downloaded it. *(Logged: Phase 1)*
- **packer-plugin-qemu:** The QEMU builder has NO `additional_iso_files` block (that is VirtualBox/vmware-ism). Extra media for Windows builds goes via `qemuargs` or, for virtio drivers, the standard pattern: `floppy_files` with recursively-copied driver directories (deterministic `A:\` paths in Autounattend `DriverPaths`). *(Logged: Phase 1)*
- **virtio-win ISO layout:** 7z path filters are exact; `balloon/w10/amd64` returns 0 files (does not exist in this build), while `viostor/w10/amd64`, `NetKVM/w10/amd64`, `vioserial/w10/amd64`, `guest-agent/qemu-ga-x86_64.msi` do. List before extracting. *(Logged: Phase 1)*
- **7z 26.04 exclusions:** `-x!*.pdb` placed after the file-path filters did NOT exclude anything — pdbs/Readme.md were extracted and blew the Packer floppy (`FAT FULL`). Prefer post-extraction `find <dir> -type f \( -name '*.pdb' -o ... \) -delete` over 7z `-x!` for staging. *(Logged: Phase 1)*
- **Packer floppies:** `floppy_files` builds a **1.44 MB** FAT image (not 2.88 MB), copies **FLATLY** (no directory structure — every file lands at the floppy root), and does **NOT template file contents** — `{{ user `var` }}` placeholders are copied verbatim into the floppy, breaking unattend passes (specialize ProductKey error: "value outside the range of acceptable values"). Render answer files yourself (sed from a `.in` template) and point `DriverPaths` at `a:\`. Verified forensically by extracting the floppy packer left in `/tmp`. *(Logged: Phase 1)*
- **pkill self-match:** `pkill -9 -f "output-win-ltsc"` matched the agent shell's OWN command line (the pattern text itself) and killed it mid-run. Bracket-trick ALL patterns (`outpu[t]-win-ltsc`) or kill by numeric PID. *(Logged: Phase 1)*
- **Packer evidence cleanup:** SIGTERM'd packer gracefully deletes the output dir and temp floppy (evidence gone); SIGKILL preserves them for post-mortem (virt-cat the qcow2). *(Logged: Phase 1)*
- **Unattend specialize "value outside the range of acceptable values":** hit with a ProductKey in specialize; placeholder interpolation and key shape were ruled out (forensic floppy extraction + sed length checks — beware: `<Key>` also matches `<Key>/IMAGE/NAME</Key>` metadata, inflating length counts). Resolution (superseded 2026-10-11): the key belongs in the **windowsPE** pass `UserData/ProductKey` with `WillShowUI=OnError` — attempt 4 accepted it ("Valid product key in blackboard") and specialize parsed clean. Keyless media is NOT an option: fatal "Windows cannot read the ProductKey setting". *(Logged: Phase 1)*
- **Windows unattend schema:** `HideOnlineActivationScreens` does NOT exist in the 19041 `Microsoft-Windows-Shell-Setup` OOBE schema — it hard-fails the oobeSystem pass with "A component or setting specified in the answer file does not exist" (unknown setting element). Documented OOBE settings: `HideEULAPage`, `HideOEMRegistrationScreen`, `HideOnlineAccountScreens`, `HideLocalAccountScreen`, `HideWirelessSetupInOOBE`, `ProtectYourPC` (`NetworkLocation` deprecated). Rule: emit only settings you can name a Microsoft doc for; extra OOBE hides are behavioral no-ops on LTSC anyway. *(Logged: Phase 1)*
- **In-use qcow2 forensics:** `virt-cat`/`qemu-img info` fail on the image while qemu holds it ("qemu-img info exited with error status 1") — SIGKILL the build first. Caveat: qemu runs `cache=writeback`, so SIGKILL drops guest writes still in RAM — post-reboot Panther log lines (OOBE phase) were lost, while the pre-reboot flushed `C:\Windows\Panther\unattend.xml` survived. Post-mortem value is highest for pre-reboot phases. *(Logged: Phase 1)*
- **Packer interrupt window:** the qemu builder deletes `output-win-ltsc` on ANY non-clean exit — including a Ctrl-C after the guest has already shut down but before post-processing/packaging. The VM window closing is NOT "build done". Cost: a complete 8.7 GB installed image destroyed (2026-10-11). Mitigation: packaging must be a packer post-processor (`shell-local ./package-box.sh`), never a follow-up step in the wrapper; wrappers print explicit do-not-interrupt banners. *(Logged: Phase 1)*
- **Sourced env files:** In `source`d files, `VAR=value with spaces` is NOT parsed as a pure assignment — bash splits at spaces and executes the first following word as a command (`10: command not found`). Quote values containing spaces. *(Logged: Phase 1)*
- **Packer HCL variables:** There is no `environment = [...]` attribute on Packer variables (terraform-ism); the env convention is `PKR_VAR_<variable_name>`. The original plan draft specified `env = ["FOLVAL_WIN_KEY"]`, which Packer would reject. *(Logged: Phase 1)*
- **MVS LTSC media layout:** NEVER judge editions by filename. `en-us_windows_10_iot_enterprise_ltsc_2021_x64_dvd_257ad90f.iso` is dual-edition (Index 1 non-IoT `EnterpriseS` + Index 2 `IoTEnterpriseS`), while `..._enterprise_ltsc_2021_..._d289cf96.iso` holds LTSC + LTSC-N. Always enumerate with `wimlib-imagex info` before writing ImageInstall metadata. *(Logged: Phase 1)*
- **rubygems `gem build`:** `spec.files` paths resolve against the CURRENT working directory, not the gemspec's own directory — building `/tmp/wfs/winrm-fs.gemspec` from the project root fails with `["lib/winrm-fs.rb"] are not files` (backtrace truncates to a cryptic `/usr/bin/gem:12`). Build with the files cwd-relative from where you invoke gem. *(Logged: Phase 1)*
- **Fedora vagrant 2.3.4 winrm gem war (resolved via stub):** `winrm-elevated (= 1.2.3)` requires `winrm-fs (~> 1.0)`; every real winrm-fs 1.x pins `rubyzip ~> 2.0`, and Fedora's system rubyzip 3.x always wins gem activation — unresolvable with real gems, and Fedora packages no rubygem-winrm\*. Working escape: hand-built EMPTY stub gem `winrm-fs 1.9.9` (no deps), installed with `gem install <gem> --install-dir ~/.vagrant.d/gems/4.0.7`; vagrant resolves plugin dependencies from that gem home without a plugins.json entry, `vagrant plugin list` is clean afterwards. Consequence: vagrant-side winrm file uploads would break (unused — Samba is the Phase 5 transfer path; Packer has its own WinRM upload, unaffected). *(Logged: Phase 1)*
- **Packer QEMU builder output dir:** a leftover `output-win-ltsc/` from a previous run — even a SUCCESSFUL one — makes the next `packer build`/`validate` abort at once ("Output directory already exists. It must not exist."). Clean it before every rebuild (the packaged .box already contains the artifact copy). *(Logged: Phase 1)*
- **vagrant-libvirt session vs system connection:** With no `uri` set, vagrant-libvirt 0.11.2 defaults to `qemu:///session` (`config.rb` finalize!: "Default to passing true for qemu_use_session if it's not set") — and on that path `CreateNetworks` returns early WITHOUT creating any libvirt networks (silent success). Symptom: `vagrant up` fails at domain start with `virDomainCreate failed: Network not found: no network with matching name 're-isolated-net'`, while `virsh -c qemu+unix:///system list --network` shows no such network, and the box image lands in the SESSION pool (`~/.local/share/libvirt/images/`) instead of `/var/lib/libvirt/images`. Fix: pin `lv.uri = "qemu:///system"` in the Vagrantfile. Never trust "no error printed" for plugin network setup — verify with `virsh list --network`. *(Logged: Phase 1)*
- **qemu-img JSON `children` trap (QEMU 11.1):** `qemu-img info --output=json` emits a `children` array whose `file` child carries its OWN `virtual-size` (= the file's on-disk size) BEFORE the top-level `virtual-size` (the disk's virtual capacity). A `grep '"virtual-size"' | head -n1` pipeline grabbed the child value and wrote `virtual_size: 10` into the box metadata for a 60 GiB image — vagrant-libvirt then created a 10G domain volume under a 60 GiB Windows install and `vagrant up` died after 15 min of "Waiting for domain to get an IP address" (Fog::Errors::TimeoutError, domain auto-removed). Parse the JSON properly (python3 `json.load(...)['virtual-size']`), never grep-match duplicated keys. Also: stale box volumes from failed `up` attempts persist in BOTH system and session pools (`virsh vol-list`) — delete them (`vol-delete`) before re-adding a corrected box, or the plugin may reuse the stale image. *(Logged: Phase 1, 2026-10-12)*
- **lab.sh ts_run arg order:** `ts_run <log> <cmd...>` — calling `ts_run bash packer/build.sh build` silently consumed `bash` as the LOG FILENAME (stray file named `bash`, empty output-build.log). Always pass the log path first. *(Logged: Phase 1, 2026-10-12)*
- **`config.winrm.timeout` is a boot-wait cap, not an operation timeout:** Vagrant's WinRM communicator wraps every `ready?` probe in `Timeout.timeout(config.winrm.timeout)` (default 1800); a firewalled guest makes the probe hang the full window, and the `Timeout::Error` escapes into `wait_for_ready`'s outer rescue → `return false` → "Timed out while waiting for the machine to boot" after ~winrm.timeout seconds regardless of `boot_timeout`. Setting it to 60 for a snappy feel killed every `up` at 61 s. Do not lower it; tune `boot_timeout` instead. *(Logged: Phase 1, 2026-10-12)*
- **`vagrant winrm -c` executes via PowerShell:** `%windir%`-style cmd expansions are NOT interpolated (arrived as a literal `C:\Users\vagrant\Documents\%windir%\...` path). Use absolute Windows paths (`C:\Windows\System32\...`) or `$env:` syntax. *(Logged: Phase 1, 2026-10-12)*
- **Zed `move_path`/`copy_path`/`create_directory` paths:** must be prefixed with the project root dir name (`folly-n-valor/host/d5/x`) — a bare in-project destination (`host/d5/x`) is rejected as "outside the project" (copy_path) or demands an approval reason (create_directory) even though read_file/edit_file accept the unprefixed form. Always prefix with the root for these three tools. *(Logged: 2026-10-12, extended 2026-10-17)*
- **Zed `write_file` empty content:** an empty-string `content` silently creates nothing ("No edits were made"). For placeholder files like `.gitkeep`, write a single newline. *(Logged: Phase 1, 2026-10-12)*
- **Steam data lookups:** steamdb.info is bot-hostile — Cloudflare managed challenge plus an explicit do-not-scrape/no-API notice (comply; do not retry). store.steampowered.com app pages can silently redirect to the store front page for delisted apps, returning unrelated content. For target-title facts, ask the user; the RE target's identity is intentionally kept out of all repo files. *(Logged: D5, 2026-10-12)*
- **virsh default URI is qemu:///session for the agent shell:** plain `virsh list` shows NOTHING even while the domain runs under qemu:///system. Always `virsh -c qemu:///system ...`. *(Logged: Phase 2, 2026-10-14)*
- **nftables input-chain drop vs host-initiated flows:** a guest-facing ruleset that only accepts specific service ports also drops the guest's SYN-ACKs to host-initiated connections — WinRM 5985 from the host never completes (curl http_code 000 timeout), and ping shows a false 100% loss because echo-replies are dropped host-side, easily misread as the guest dropping ICMP. Fix: `ct state established,related accept` at the top of the guest-policy chain; the guest can still only initiate to the allowed services. *(Logged: Phase 2, 2026-10-14)*
- **qemu-ga guest-exec lifecycle:** the exec call returns a pid whose status must be fetched IMMEDIATELY via `guest-exec-status` — pids are reaped quickly (a delayed fetch fails with PID does not exist). `guest-file-read` requires a handle from `guest-file-open` first; reading by path is impossible. Windows argv quoting: the guest agent joins args with spaces without re-quoting, so a PowerShell `-Command` string containing an unquoted multi-word argument (e.g. `-DisplayGroup Windows Remote Management`) arrives word-split — embed escaped quotes around inner strings, or avoid spaces in parameters. PowerShell cold start can take ~10 s: give the exec call itself a 30 s timeout. *(Logged: Phase 2, 2026-10-14)*
- **tcpdump reverse-resolves IPs in text output:** `tcpdump -r file | grep 8.8.8.8` finds nothing because the address prints as `dns.google`. Use `-n` when reading, or grep by hostname. Also: `timeout N tcpdump -w file` truncates any previous capture on start (plain `-w` overwrites) — a still-running dump started mid-diagnosis silently destroyed earlier evidence once. *(Logged: Phase 2, 2026-10-14)*
- **Windows guest WinRM listener vs firewall rules:** a running `WinRM` service with `netstat` showing `0.0.0.0:5985 LISTENING` is not enough — if both `Windows Remote Management (HTTP-In)` firewall rules are disabled, host connections time out silently. After any unclean shutdown, verify the rules (`Get-NetFirewallRule -DisplayGroup ...`) and the active profile (an isolated NIC is Unidentified → Public). Also expect WinRM to come up minutes after the domain reports running. *(Logged: Phase 2, 2026-10-14)*
- **NCSI hermetic loop is normal:** a sealed Windows guest retries `www.msftconnecttest.com/connecttest.txt` (and edge/telemetry endpoints) forever, generating continuous DNS+HTTP entries in the gateway log. Not a fault; a free liveness signal. `curl.exe -o NUL` inside `vagrant winrm -c` breaks (NUL parsed as an output-format parameter) — drop the `-o`/`-w` flags when invoking curl.exe through PowerShell. *(Logged: Phase 2, 2026-10-14)*
- **strace masks SELinux domain transitions (cost a full debug round):** running a binary under strace/ptrace suppressed the `unconfined_t → netutils_t` transition, so tcpdump-under-strace wrote to a `user_home_t` dir successfully while the same command without strace got EACCES — the strace "probe" disproved the correct hypothesis. Never use a strace run to rule SELinux in or out. *(Logged: Phase 3, 2026-10-15)*
- **tcpdump's SELinux domain on Fedora is `netutils_t`, not `tcpdump_t`:** every grep for `tcpdump`/`tcpdump_t` AVCs came up empty and sent the investigation down DAC/systemd-sandboxing rabbit holes. Resolve the actual domain from the AVC `scontext` (or `ps -Z`), not from the binary name. *(Logged: Phase 3, 2026-10-15)*
- **Service writing to a user-owned dir needs BOTH file rules and `dac_override`:** even running as root, using CAP_DAC_OVERRIDE on a user-owned path is an SELinux-gated operation — `netutils_t` was denied `{ dac_override }` (tcontext=self) after `user_home_t` write rules were allowed. A service dropping privileges (`-Z root`, uid/gid drop) also needs `setuid`/`setgid`/`chown`. See `host/selinux/folval-pcap.te`. *(Logged: Phase 3, 2026-10-15)*
- **audit2allow is piecemeal:** it only allows the exact denied permission classes seen in the audit window — the first generated module granted `dir search` but not `add_name`/`create`/`dac_override`, so the failure persisted identically. For a known root cause, hand-write the .te with the full permission set (dir+file+capability) instead of iterating audit2allow rounds. Also: `ausearch --no-pager` is invalid (ausearch has no pager); grep/tail its output instead. *(Logged: Phase 3, 2026-10-15)*
- **Reboot-survival of host boundary:** manually-applied nftables rules vanish on reboot — a host reboot mid-session silently removed the isolation boundary and broke gateway startup (EADDRNOTAVAIL). Rules now load via `folval-firewall.service` from `/etc/folval/folval.nft`. A systemd unit (init_t) silently fails AVC-reading files under `/home` — never point unit ExecStart at repo checkout paths. *(Logged: Phase 3, 2026-10-15)*
- **Windows NLA caches its connectivity verdict:** after fixing the gateway to serve genuine NCSI responses, `Get-NetConnectionProfile` kept reporting LocalNetwork until a guest reboot (restarting NlaSvc times out on dependents). Plan a reboot after NCSI-affecting changes. *(Logged: Phase 3, 2026-10-15)*
- **`Disable-ScheduledTask -TaskName` alone fails 0x80070002** even though `Get-ScheduledTask` lists the task — pass `-TaskPath` too (and keep a `schtasks.exe /Change /TN <path> /Disable` fallback); LTSC 2021 no longer ships KernelCeip/MareBackup. *(Logged: Phase 3, 2026-10-15)*
- **SELinuxContext= on a systemd unit for tcpdump breaks exec (203/EXEC):** forcing unconfined_u/system_u contexts denies `entrypoint` on `netutils_exec_t`. Never re-add it; fix policy (or label the target dir) instead. *(Logged: Phase 3, 2026-10-15)*
- **PowerShell progress output wedges qemu-ga permanently:** Invoke-WebRequest under guest-exec renders progress bars into the captured stdout; one guest-exec-status reply >10 MB exceeds virsh's read buffer ("No complete agent response found in 10485760 bytes", EOVERFLOW) and the channel then deadlocks — qemu-ga keeps offering the response libvirt refuses to read; every later virsh agent call fails with "Guest agent is not responding". The guest itself is fine (NCSI cadence uninterrupted) and the script usually completes. ACPI reboot (`virsh reboot`) is swallowed; only `virsh destroy` + `start` recovers. Rule: every guest script sets `$ProgressPreference = 'SilentlyContinue'` first (also kills the progress overhead). vagrant-libvirt also uses the agent for WinRM address discovery, so a wedged agent blocks the WinRM path too. *(Logged: D5 push, 2026-10-17)*
- **folval-capture boot race:** after a host reboot, libvirt creates virbr1 some time after libvirtd reports started; tcpdump started before the bridge existed, failed "No such device", and the default start limit (5 fast retries) gave up. Fix: ExecStartPre wait loop on /sys/class/net/virbr1 + RestartSec=5 + StartLimitIntervalSec=0 in [Unit] (it is a [Unit] key — systemd-analyze flags it in [Service]). *(Logged: 2026-10-17)*
- **SELinux allows are per-TYPE and path resolution walks EVERY component:** folval-capture failed EACCES with ZERO AVCs although the module allowed netutils_t create/write on user_home_t — because /home (home_root_t) and /home/<user> (user_home_dir_t) are different types and the module lacked dir search on them; the base policy DONTAUDITS home-dir search for system domains, so the denial never logged. Diagnose with `stat -c %C` on each path component. Never conclude "not SELinux" from absent AVCs alone — dontaudit'd denials are invisible; `semodule -DB` (then `-B` to restore) makes them log. Same for assuming a hand-written module replaces an audit2allow one: diff against the real (dontaudit-disabled) AVC history or the old module's rules. *(Logged: 2026-10-17)*
- **tcpdump ring-buffer filenames:** with -W N -C S, output files are <base>00..<base>(N-1); the bare base name is never written by the ring. A file named exactly like the base (folval.pcap) is an artifact of an older NON-ring run — reading it shows ancient history; check mtimes before trusting a pcap. *(Logged: 2026-10-17)*
- **Windows ping statistics count ICMP errors as Received:** blocked probes get "Reply from <gateway>: Destination ... unreachable" which ping tallies as Received → "0% loss" even when 100% blocked (false-positived the D5 gate). Real echo replies are lines matching 'Reply from <target>: bytes=' — count those (host/d5/d5-gate.ps1). *(Logged: 2026-10-17)*
- **Crash-looping service + RestartSec=5 + StartLimitIntervalSec=0:** restart counter × 5 s approximates the loop start time; journalctl tail shows only the last seconds of an hours-long loop. Compute the window first, then query by time. *(Logged: 2026-10-17)*
- **Steam client purges steamcmd-staged app content** when a dependency app is absent from the staged set — host-side staging into a guest library is not a reliable install path; let the in-guest client install during the audited window (D5, see host/d5/RUNBOOK.md). Related: the client's self-update hangs at "checking available updates" against the DNS sinkhole — the window must disable the isolated NIC (d5-net-window-on/off.ps1) so the NAT path is the only egress. *(Logged: 2026-10-17)*
- **virsh detach-interface** requires --type + --mac + --live (no --source flag); find the MAC via domiflist. *(Logged: 2026-10-17)*
- **PowerShell 5.1 Get-ChildItem -Include** only works as expected with -Recurse (or with a wildcard path); plain `-Include` on a literal dir returns nothing. *(Logged: 2026-10-17)*
- **tcpdump `-n` still prints service NAMES for well-known ports in text output** (443 → `.https`, 80 → `.http`): a numeric-only grep aggregation (`'> [0-9.]+\.[0-9]+:'`) silently dropped every 443 flow during port profiling and briefly under-reported the title's footprint to just the one custom high port. Aggregate with `-nn`, or match service names too. *(Logged: D3 wire profiling, 2026-10-17)*
- **pcap coverage = ring/service start time vs event time:** an event earlier than capture (re)start is legitimately absent from the ring; compare timestamps before concluding "not captured" (and before claiming something IS captured — the ring's first packet bounds coverage from below). *(Logged: D3 wire profiling, 2026-10-17)*
- **Console apps cannot be Windows services:** `sc create` on a binary that never calls `StartServiceCtrlDispatcher` (e.g. frida-server) always fails the SCM handshake — start times out (1053), the service is marked FAILED, and the process may be killed — even though the binary runs fine standalone. Persistence without a wrapper binary (nssm): SYSTEM scheduled task, `/SC ONSTART /RU SYSTEM /RL HIGHEST`. *(Logged: Phase 4, 2026-10-17)*
- **frida-server listens on localhost by default:** without `-l` it binds `127.0.0.1:27042` only — the host can never reach it. Always pass `-l 0.0.0.0:27042` (or the interface IP). *(Logged: Phase 4, 2026-10-17)*
- **WinRM sessions reap their child processes:** a `Start-Process` spawned inside a WinRM exec looks healthy in-session (process listed, port LISTENING) but dies with the session — a later session sees no process and the host `nc` times out. Start daemons from a session-detached context (Task Scheduler via `schtasks /Run`), never via bare `Start-Process` in a one-shot WinRM command. *(Logged: Phase 4, 2026-10-17)*
- **Windows Firewall default-inbound-block bites hermetic listeners:** `0.0.0.0:27042 LISTENING` in guest netstat is unreachable from the host until an inbound rule exists (isolated NIC profile = Public). Add a subnet-scoped rule (`netsh advfirewall firewall add rule dir=in localport=27042 remoteip=<lab>/24`), not a wide-open one. *(Logged: Phase 4, 2026-10-17)*
- **schtasks stores /TR verbatim — verify after create:** a PowerShell single-quoted string passed as the task command lands LITERALLY (an unexpanded `$Var` becomes the stored command line; task fails 0x80070002 file-not-found at run time). Check `schtasks /Query /TN <name> /V` "Task To Run" after every create; a failed `schtasks /Run` surfaces only as `Last Result: -2147024894` (0x80070002) in the same output. *(Logged: Phase 4, 2026-10-17)*
- **qemu-ga stays wedged across sessions until destroy+start:** the D5-era EOVERFLOW wedge (see progress-bar entry) persisted — `guest-exec` itself now times out ("guest agent didn't respond within 5 seconds"). `host/tools/guest-run.sh` detects any exec failure or `guest-exec-status` "PID does not exist" and re-runs over WinRM automatically; `guest-winrm.sh` gained `-c '<ps>'` inline form. Scripts run this way must stay idempotent (fallback re-runs). *(Logged: Phase 4, 2026-10-17)*
- **Correlate connection attempts against a FULL census of the window, not the expected-hostname set:** the custom-port SYN chains had no precursor in a grep scoped to the two known title hostnames, so they were mis-attributed to one of them via assumed cycle order — the real precursor was a third, publisher-owned hostname outside the grep set (sub-millisecond DNS→SYN, twice). A scoped grep answers only the scoped question: "no precursor found" means "none in the set searched". Re-census whenever the observation window grows. *(Logged: D3 wire profiling correction, 2026-10-17)*
- **frida CLI always enters its REPL:** `-q` only hides the banner — after `-l`/`-e` loads, the CLI waits on stdin. `</dev/null` makes it exit after the script runs (acceptable for one-shots), but the deterministic path is the Python API: `host/tools/frida-run.sh` wraps it (`add_remote_device` → attach/spawn → `create_script` → bounded wait → clean detach). Routing: `console.log` goes to the script's LOG handler (`set_log_handler`), NOT the `on("message")` callback — that only sees `send()` and errors. frida does not kill spawned processes on detach; the runner does (`dev.kill`). *(Logged: Phase 4, 2026-10-17)*
- **qemu-ga guest-exec output keys are `out-data`/`err-data` (base64), present only with `"capture-output": true`:** there is no "stdout" key — a runner that omits the flag and reads `stdout` reports success with EMPTY output while the guest command ran fine (silent-failure mode; bit the guest-run.sh rewrite, confirmed live: schtasks query printed nothing). Decode both keys and propagate `exitcode`. *(Logged: Phase 4, 2026-10-17)*

## Verified Command Patterns

- **exiftool 13.50 (`host-side metadata triage of Windows/RE artifacts`):** user-installed via `sudo dnf install perl-Image-ExifTool` (agent has no sudo); Fedora package `perl-Image-ExifTool-13.50-2.fc45` provides `/usr/bin/exiftool`.
  - Command: `exiftool <pe_file>` — instant PE triage without Ghidra: version resources (CompanyName, FileDescription, File/Product Version, OriginalFileName), PE header facts (Machine, PE Type, Subsystem, Linker Version, Entry Point, Code Size), build Time Stamp, and the embedded **PDB path** (leaks the vendor's build tree). Verified on a Win64 virtio service binary.
  - Command: `exiftool <msi_file>` — MSI is an OLE compound file (exiftool labels the type `FPX`); reads the SummaryInformation stream: Title/Subject/Author/Template (`x64;1033`)/Revision-Number GUID/build dates. Verified on the qemu-ga MSI.
  - Command: `exiftool <iso_file>` — reads ISO9660 volume descriptors only (Volume Name, Publisher, Data Preparer, imaging-software version, El Torito boot flag, volume create dates); it does NOT list file contents — content listing stays with `7z l` (see bsdtar/UDF warning above).
  - Command: `exiftool -j <file>` — JSON for scripting; verified on the 6.3 GB `.box` (identified as GZIP). It also identifies file types (a shell script → `bash script` / `text/x-bash`); files with no format metadata get only file-system tags.
  - Factual: purely read-only unless tag-assignment args are passed; writes to unsupported formats fail cleanly (`Writing of TXT files is not yet supported`, "0 image files updated"). A successful write preserves the original as `<file>_original` (verified on a scratch PNG); `-overwrite_original` suppresses that backup (verified) — but a pre-existing `_original` from an earlier write is left behind either way. Lab policy: read-only on evidence; copy to `/tmp` for write experiments. *(Verified: 2026-10-12)*
